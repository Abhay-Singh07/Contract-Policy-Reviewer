2. 🔴 Biggest issue: your Compliance Agent is NOT actually using the DPDP/IT Acts yet

This is the most important thing I noticed.

Your README says:

"scoped to Indian law (DPDP Act 2023, IT Act 2000)"

and your Compliance Agent prompt tells the LLM to check against those laws.

But your actual retrieval system currently does this:

Clause
 ↓
find_similar_findings()
 ↓
finding_memory
 ↓
past findings
 ↓
ALL THREE agents

Your memory.py searches FindingMemory, which contains previous findings.

And dispatch_specialists() retrieves those findings and passes the same memory context to:

Risk
Compliance
Ambiguity

Your ingestion scripts technically load the regulation JSON files, but they put them into the same FindingMemory table as previous findings. load_regulations.py explicitly comments that this is a temporary reuse and that a dedicated model should eventually replace it.

This is what I would change.

Instead of:

FindingMemory
├── past risk findings
├── past compliance findings
├── standard clauses
└── regulations

make separate knowledge types:

FindingMemory
    ↓
past reviewed findings

    ↓

    ↓

Then:

Compliance Agent
      ↓

      ↓
DPDP / IT Act chunks

while:

Risk Agent
      ↓
StandardClauseRetriever
      ↓
similar contract clauses

That would make your architecture much more semantically correct.

3. 🔴 Your RAG query embedding is currently wrong

This is a real technical issue.

Your CohereEmbeddingClient.embed() always uses:

input_type="search_document"

But memory.py uses this same method for the query:

query_vector = embed_client.embed([clause_text])[0]

For semantic search, Cohere distinguishes between:

Documents → search_document

Queries → search_query

Cohere's current documentation explicitly recommends search_query for the query side and search_document for stored documents.

So you should eventually have something like:

embed_documents(...)
embed_query(...)

rather than one generic:

embed(...)

Conceptually:

Ingestion:

Act chunk
   ↓
embed_document()
   ↓
pgvector


Runtime:

Contract clause
   ↓
embed_query()
   ↓
pgvector

This is important before you evaluate whether your RAG is actually working.

4. 🔴 Your Cohere implementation may need updating

Your code currently does:

resp = self._client.embed(...)
return resp.embeddings

But current Cohere examples explicitly request float embeddings and access:

response.embeddings.float

and current semantic-search examples use ClientV2.

So before you rely on live Cohere retrieval, I'd update embeddings.py to match the version of the SDK you're actually installing.

This is particularly important because your requirements file currently says simply:

cohere

with no version pin.

For your local project, that's okay while experimenting, but it means a future pip install could pull a different SDK version.

5. 🔴 Your "mock embeddings" don't test semantic retrieval

This is subtle but important.

Your mock does:

SHA256(text)
     ↓
repeat bytes
     ↓
vector

So:

"uncapped liability"

and:

"unlimited damages"

don't become semantically similar.

They become unrelated deterministic hashes.

Therefore:

MockEmbeddingClient

is useful for testing:

"Does my database/vector pipeline work?"

but not:

"Does my RAG actually retrieve semantically relevant information?"

So your tests can prove the plumbing works without proving that the retrieval is good.

That's fine for now, but eventually you need a real Cohere test with a few known queries and expected top results.

8. 🔴 Re-reviewing the same document is currently problematic

This is one of the biggest actual application issues.

Suppose you do:

Upload NDA
 ↓
Review
 ↓
Works

Then click review again.

Your existing clauses already have IDs.

Then save_clauses() tries to insert them again:

id=c.clause_id

into the database.

Since Clause.id is the primary key, you're going to get a duplicate-key problem.

And Report.document_id is also unique:

document_id ... unique=True

so you can't simply create another report for the same document either.

For local testing

You can simply say:

One review per uploaded document.

But I'd eventually support:

Document
   │
   ├── ReviewRun 1
   ├── ReviewRun 2
   └── ReviewRun 3

That's actually the better production architecture.

15. 🟠 QA has an interesting limitation

Your QA prompt says:

requeue if specialists clearly missed something obvious.

But qa_agent.py immediately returns:

if not findings:
    return findings, False

So if all three specialists completely miss an obvious issue, QA never gets called with an empty finding set.

Therefore:

Specialists miss everything
        ↓
findings = []
        ↓
QA returns immediately
        ↓
no requeue

Your QA can currently reject bad findings, but it cannot really detect:

"You guys found nothing, but this clause obviously has a problem."

If that's intentional, fine.

If you want true self-critique, you'd eventually change QA to receive the clause even when findings are empty and allow:

{
  "decisions": [],
  "needs_requeue": true
}

That's a worthwhile improvement.

20. 🟠 Your database transaction handling could improve

Your CRUD functions each do:

db.commit()

For example:

create document → commit
save clauses → commit
save findings → commit
save report → commit

That means a failure halfway through can leave partial data.

For example:

Document saved
Clauses saved
Findings saved
Report FAILED

Now you have an incomplete review.

Eventually I'd prefer:

BEGIN TRANSACTION

save document
save clauses
save findings
save report

COMMIT

or:

ROLLBACK

if something fails.

Again: not necessary to block your local testing, but definitely something to fix before calling it production-ready.
